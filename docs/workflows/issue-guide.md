# 이슈 작성 가이드 (Issue Creation Guide)

이 문서는 프로젝트에서 사용하는 이슈(Issue) 작성 규칙을 안내합니다.
모든 작업은 이슈 생성을 통해 공유하고 추적하는 것을 원칙으로 합니다.

---

## 0. 이슈의 목적

- 작업 내용과 목표를 명확하게 정의합니다.
- 팀원 간 진행 상황을 투명하게 공유합니다.
- 변경 이력과 그 배경을 기록하여 프로젝트의 히스토리를 관리합니다.

---

## 1. 이슈 작성 기본 원칙

- **하나의 이슈는 하나의 작업 단위**: 두 개 이상의 독립적인 작업을 하나의 이슈에 담지 않습니다.
- **명확하고 간결한 제목**: 제목만으로 이슈의 내용을 짐작할 수 있도록 작성합니다.
- **일관된 타입 명시**: 작업의 종류를 명확히 하기 위해, 제목에 타입을 명시합니다. 이슈 타입은 [커밋 컨벤션](./commit-convention.md)과 동일한 타입을 사용합니다.
- **담당자(Assignee) 및 레이블(Label) 지정**: 이슈 생성 시 담당자와 `feat`, `fix`, `docs` 등 적절한 레이블을 반드시 지정합니다.

---

## 2. 주요 이슈 타입별 작성 가이드

### 2.1. `feat`

- **목적**: 새로운 기능을 제안하고 명세를 정의할 때 사용합니다.
- **제목 형식**: `[feat] <기능 요약>`
- **예시**: `[feat] 마이페이지에 소셜 로그인 연동 기능 추가`

---

#### `feat` 이슈 본문 템플릿

```md
### 1. 배경 (Why)

- 왜 이 기능이 필요한가요? 어떤 문제를 해결할 수 있나요?
- e.g., 사용자들이 일반 회원가입보다 소셜 로그인을 선호하여 이탈률을 줄이고자 합니다.

### 2. 기능 명세 (Specification)

- 기능이 어떻게 동작해야 하나요?
- - [ ] 사용자는 마이페이지에서 '소셜 계정 연동' 버튼을 클릭할 수 있다.
- - [ ] 구글, 카카오 계정 연동을 지원한다.
- - [ ] 계정 연동 후에는 해당 소셜 계정으로 로그인이 가능하다.

### 3. 성공 기준 (Acceptance Criteria)

- 어떤 조건이 충족되어야 이 기능이 완료된 것으로 간주할 수 있나요?
- e.g., 구글 계정 연동 후, 로그아웃하고 구글 로그인 버튼으로 재로그인이 성공적으로 이루어진다.

### 4. (선택) 참고 자료

- (디자인 목업, 관련 문서, 참고 URL 등이 있다면 여기에 첨부)
```

---

### 2.2. `fix`

- **목적**: 소프트웨어의 오류, 예상과 다른 동작 등 버그를 보고할 때 사용합니다.
- **제목 형식**: `[fix] <버그 내용 요약>`
- **예시**: `[fix] 로그인 페이지에서 패스워드 입력 시 화면 깨짐`

---

#### `fix` 이슈 본문 템플릿

```md
### 1. 발생 환경

- **OS**: e.g., Windows 11, macOS Sonoma
- **Browser**: e.g., Chrome 124.0.0
- **Version**: e.g., v1.0.1

### 2. 재현 단계

1. '로그인' 페이지로 이동합니다.
2. 아이디를 입력합니다.
3. 패스워드를 입력하면...

### 3. 실제 결과 (Actual Behavior)

- 화면 UI가 깨지면서 입력이 불가능해집니다.

### 4. 예상 결과 (Expected Behavior)

- 패스워드가 정상적으로 입력되어야 합니다.

### 5. (선택) 스크린샷 또는 로그

- (화면 캡처나 관련 로그가 있다면 여기에 첨부)
```

---

### 2.3. `docs`

- **목적**: 문서의 추가, 수정, 삭제가 필요할 때 사용합니다.
- **제목 형식**: `[docs] <문서 작업 요약>`
- **예시**: `[docs] 브랜치 전략 가이드에 hotfix 절차 추가`

---

#### `docs` 이슈 본문 템플릿

```md
### 1. 목표 (Objective)

- 이 문서 작업의 최종 목표는 무엇인가요?
- e.g., 신규 입사자가 hotfix 브랜치 작업 절차를 명확히 이해하도록 돕는다.

### 2. 세부 할 일 (To-Do List)

- - [ ] hotfix 브랜치 분기 지점 명시
- - [ ] main/dev 브랜치 동기화 방법 설명 추가

### 3. 완료 조건 (Definition of Done)

- e.g., `branch-stratagy.md` 파일에 hotfix 관련 내용이 업데이트된다.
```

---

### 2.4. `chore`

- **목적**: `feat`, `fix`, `docs`에 속하지 않는 기타 작업을 등록할 때 사용합니다. (예: 리팩토링, CI/CD 설정, 테스트 코드 개선, 의존성 업데이트 등)
- **제목 형식**: `[chore] <작업 내용 요약>`
- **예시**: `[chore] CI 워크플로우에 테스트 커버리지 측정 단계 추가`

---

#### `chore` 이슈 본문 템플릿

```md
### 1. 목표 (Objective)

- 이 작업의 최종 목표는 무엇인가요?
- e.g., 매 PR마다 테스트 커버리지를 측정하고 리포트를 생성하여 코드 품질을 관리한다.

### 2. 세부 할 일 (To-Do List)

- 목표를 달성하기 위해 필요한 구체적인 작업 목록입니다.
- - [ ] Codecov 연동
- - [ ] CI 스크립트에 커버리지 측정 및 업로드 명령어 추가
- - [ ] 관련 설정 문서를 `docs/setup.md`에 업데이트

### 3. 완료 조건 (Definition of Done)

- 어떤 상태가 되면 이 작업이 완료된 것으로 볼 수 있나요?
- e.g., PR 생성 시 Codecov 리포트가 정상적으로 댓글에 등록된다.
```

---

### 3. 기타 커밋 타입

`refactor`, `style`, `test` 와 같은 커밋 타입은 일반적으로 독립적인 이슈를 생성하기보다는 `feat`나 `chore` 이슈의 일부로 진행되는 경우가 많습니다. 만약 리팩토링이나 테스트 개선 범위가 클 경우, `[chore]` 타입의 이슈를 생성하여 작업을 추적하는 것을 권장합니다.
